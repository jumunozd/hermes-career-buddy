# P-6 Baserow as the system's real record (status: APPROVED 2026-11-19, AP-c19aab8213487acf07d7bf5a; option A)

Replaces MIG-01 (config/baserow-mapping.yaml), which only added four fields.

## Findings (live check, 2026-11-19)
- Table 839 has **5 rows, all test rows** from the October integration tests. No real job was ever written.
- Cause: `features.baserow_live_writes` is false by design (user approval + token permission pending since
  the first build). Every run since RT-13 did a dry-run preview only.
- Everything the system found lives locally in `private/`: the Seen log (238 distinct jobs scanned; 20 kept
  for review, the rest excluded with a reason), run snapshots, saved ads and the prepared packages
  (Stornoway, TasPorts, Shaw, Nyrstar networking CV).
- The schema (11 fields) was built for a manual application tracker. Hermes needs more: category,
  alignment group, why an offer waits for review, source, dates, contact, latest version. Today all of that
  would be squeezed into a `[hcb v1]...` tag line inside Notes: readable by code, but not queryable by a future dashboard (one free-text line per row).

## Decision by the user (2026-11-19)
"El sistema solamente debe guardar los que no están descartados." Baserow is **Hermes's own database**:
the system reads and writes it to run. It is not the human view: a future front-end will read Baserow and
show the user a dashboard. So the schema is designed for machines (one field per fact, stable keys, no
free-text tags as the main record), which is also what a dashboard needs to query.

## Change
### 1. What goes into Baserow (and what does not)
- **In:** every opportunity the system keeps (shortlisted, pending review, exploratory), every one the user
  asks to prepare, and every application. These are records the user acts on.
- **Not in:** excluded jobs (other profession, out of zone, Senior/Manager, expressions of interest). They stay
  in the Seen log with their reason; `bin/hcb` can export them as CSV any time (as on 2026-11-17).

### 2. Schema v2 for table 839 (keep the 11 fields, add 12)
| Field | Type | Filled by |
|---|---|---|
| Opportunity Ref | text (unique key) | system: stable id, replaces the `o-xxxxxx` codes |
| Ranking Category | single select: principal, exploratoria, pendiente_revision, fuera_de_ranking | system |
| Alignment Group | single select: A, B, C, D, E, none | system (target catalogue) |
| Catalogue Title | text | system |
| Review Reason | text | system ("confirmar localidad", "revisar funciones") |
| Entry Signal | single select: Strategic Entry, Neutral | system |
| Fit | number (0-100) | system, only after A-H at preparation |
| Source | single select: TSS, Council, Employer site, SEEK (pasted), LinkedIn (pasted), Email alert | system |
| Posted Date | date | system, when the ad states it |
| Discovered | date | system |
| Ad Contact | text (name + phone from the ad) | system |
| Latest Version | text (`prep-001/v3`) | system |

Status options: add **Closed** (expired, never deleted). Category no longer needs to live in Status.
The `[hcb v1]` tag block stays in Notes as a fallback and audit trail, not as the main view.

### 3. Steps (in order)
1. Backup of Baserow (user: export table 839 to CSV, or snapshot the `baserow_data` volume).
2. The user adds the 12 fields and the Closed option in Baserow, or pastes a short-lived admin token in
   Baserow itself so Claude Code applies them (a database token cannot change the schema).
3. The user gives the dedicated token Create + Update on table 839 (never Delete).
4. Claude Code updates `config/baserow-mapping.yaml` and `hcb/baserow.py`, runs the schema check.
5. Backfill, dry-run first: the 20 kept jobs and the prepared packages -> preview -> user approves -> live
   write -> read-back. The 5 test rows are left for the user to delete.
6. Turn on `features.baserow_live_writes`; every run then registers its kept offers, and the digest shows the
   Baserow ID instead of `o-xxxxxx`.

## Success criteria
- Schema check matches v2 with no drift; backfill read-back equals the preview.
- One weekday run creates rows for its kept offers; a second run creates none for the same jobs (dedup).
- `Prepara la oferta <Baserow ID>`, `Enviada <ID>` and `Cerrada` work against the real rows.

## Rollback
`features.baserow_live_writes: false`; delete the added fields/option; restore the backup.
