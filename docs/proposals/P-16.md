## Changes
1. **No images in the agents' process: layout as data (biggest gain; the user, 2026-11-28: "son robots, no
   necesitan conversar con imágenes").** fit.py already renders every document in headless Chrome to measure it.
   It writes `layout.json`: per page, % used, first and last block, any heading left alone at the bottom, any role
   split across pages, whether the letter's signature fits. The Writer and the Recruiter read that file; no page
   images are created or analysed (`vision_analyze` is no longer part of preparation). The only person who looks at
   the documents as images is the user, who opens the PDF before sending. Expected: ~465k fewer characters in the
   Writer's context per preparation.
   **Safeguards for form problems that only rendering shows** (all code, no model, no images in the run):
   a. *Render checks in the same Chrome pass* (`layout.json`, FAIL in `bin/hcb engine run`): the template fonts
      actually loaded (no silent fallback font); no two text blocks overlapping; no text overflowing its box or the
      page margins; no empty page.
   b. *PDF text = source text* (ats_check.py, which already extracts the PDF text with PDFKit): every heading,
      bullet and paragraph of content.json is present in the PDF in order, nothing truncated, no garbled characters
      (e.g. "â€™"); same for the DOCX text.
   c. *Golden render test in the test suite*: the demo persona's CV and letter are rendered and compared with an
      approved reference picture (pixel difference over a threshold fails). It runs whenever engine/template code
      changes (pre-commit and CI), so a template or font break is caught once, before it reaches any application.
   d. *Escape hatch*: if a or b flags something it cannot classify, the Writer may look at that ONE page image, at
      low detail, and must say why in `layout.json`.
2. **PM conversation kept short.** `compression.idle_compact_after_seconds: 3600` in the career-buddy profile (a
   thread you come back to after an hour is compacted before the first reply), and the PM ends each delivered
   package with a pointer to its files (the facts live in files and Baserow, never only in the chat). The user may
   also type `/new` at any time. If Hermes offers a daily automatic session reset for Telegram, use it (to verify
   during the build).
3. **Compact engine output.** `bin/hcb engine run --brief` returns only failing steps, each in one line with the
   fix hint, plus `all_passed`; the full JSON stays in `engine-validation.json`. The Writer uses `--brief`.
4. **Writer pack by section.** `bin/hcb writer-pack --plan <document-plan.json>` writes only the method sections the
   plan needs (no selection-criteria section without a statement, no letter section without a letter) and the
   facts digest without `context_only` cards that `selection.json` left OUT. Large reads (>20k chars) are replaced
   by `search_files` / ranged reads.
5. **One voice pass.** Soul Voice and Humanizer applied together with one combined checklist
   (`references/voice-layers.md`), Soul Voice still winning; one `voice_review` block. Same rules, one round trip
   instead of two or three.
6. **Timing per phase.** `state.event("phase", task_id, role, phase, started_at, ended_at)` for intake, Writer
   draft, engine runs, voice, Recruiter rounds; `bin/hcb dashboard` shows minutes per phase for the last
   preparations, and the Saturday report the median.
7. **Lower reasoning for mechanical steps (optional).** `delegation.reasoning_effort: low` only for delegated
   revise / claim-map tasks if Hermes supports per-task effort; the main Writer draft and the Recruiter keep
   `medium`. Measured with 6 before switching.

  and Recruiter results.
