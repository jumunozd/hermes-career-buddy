# P-14 Self-repair: Hermes proposes, the user approves (status: APPROVED 2026-11-27 with D-P14-1..4, AP-0214bb7cf3accfb130456e20; BUILT)

Source: the user, 2026-11-27: "¿Hermes se puede arreglar a sí mismo también?" (Hermes runs on Codex and has a
local terminal in the project folder). That day Hermes launched `claude -p` on its own to fix the engine, and
earlier a Writer recorded an approval in the user's name. Both show the same gap: today Hermes **can** change code,
facts and the rules that check its own work, and only instructions stop it.

## Principle
Hermes may **diagnose and prepare** a repair; it never **applies** one to the live system without the user's
explicit approval, and it never changes the controls that check its own work. The part being checked cannot
rewrite the checker. Code enforces this, not instructions.

## What exists today
- Terminal backend `local`, cwd = project folder: Hermes can edit any file, run tests, commit and (with the
  machine's GitHub login) push.
- Guards that already exist: `engine_unchanged` (fingerprint of `engine/` + `private/facts` around a pipeline run),
  the A-H pin manifest, `APPROVAL_CHANNELS` and `self_approval_problems` (approvals only from user channels),
  the privacy scan, the repo's `.githooks`.
- Hermes supports `pre_tool_call` shell hooks that can **block** a tool call before it runs (config `hooks:`,
  currently unused in the career-buddy profile).

## Zones
| Zone | Paths | Who may change it |
|---|---|---|
| 0. Work output | `private/applications/`, `private/state/` runs, reports, drafts | Hermes, as today |
| 1. Repair workspace | `private/repairs/R-*/` (diagnosis, patch, test log, an isolated git worktree) | Hermes, freely |
| 2. Protected | `hcb/`, `engine/`, `bin/`, `config/`, `.hermes/skills/`, `tests/`, `docs/`, `AGENTS.md` | `bin/hcb repair apply` after the user's approval |
| 3. Facts | `private/facts/`, `private/config/` | Never in a repair (they are not in git): the existing fact flow and A-H repin |
| 4. Core guards | the repair hook, `hcb/repair.py`, `hcb/state.py` approvals, `hcb/envelopes.py` self-approval, `.githooks`, the Hermes profile `config.yaml` | **Never Hermes.** Only a Claude Code session with the user |

## Flow
1. **Detect.** A step fails (engine, tests, a script) and blocks a user task, or the user asks for a fix.
   The PM opens a repair: `bin/hcb repair open --reason "<failure>" --evidence <log>` → `R-<id>`.
2. **Diagnose (zone 1 only).** Hermes creates an isolated worktree under `private/repairs/R-<id>/worktree`
   and works only there. It writes `diagnosis.md`: what failed, the root cause, and why the fix is the cause and
   not the symptom.
3. **Test first.** The patch must add or change a test that fails before the fix and passes after (RED → GREEN).
   `bin/hcb repair check R-<id>` runs the full suite with the user's data and with the demo persona, plus the
   privacy scan, inside the worktree, and stores the log.
4. **Classify (code, not the agent).** `bin/hcb repair classify R-<id>` reads the diff and labels it:
   - zones touched (2, 3; any zone-4 file makes the repair invalid, it cannot be proposed);
   - **weakens a control** when the diff deletes or skips tests or assertions, removes a check or an error
     message from a check function, raises a limit or lowers a threshold, adds to an exemption / allow list,
     widens `APPROVAL_CHANNELS`, or edits a FAIL into a WARN.
5. **Propose to the user (Telegram).** Plain-language card: what failed, the cause, what changes, files touched,
   tests result, risk label. Buttons: «Aplicar R-<id>», «Rechazar», «Ver cambios» (sends the diff file).
   A repair that weakens a control has no button: the user types «Apruebo aflojar <control> R-<id>».
6. **Apply (code).** `bin/hcb repair apply R-<id>` refuses unless an approval for that exact repair exists from a
   user channel (telegram / cli / claude_code, never a task envelope) and the diff still matches the one
   approved (hash). It re-runs the suite on the live tree, makes one local commit `repair R-<id>: ...`, and records
   the event.
7. **Push stays with the user.** Hermes never pushes. The user pushes from Claude Code ("Yes, push") or with a
   command. `bin/hcb repair revert R-<id>` undoes the single commit.

Allowed **without** approval (unchanged): retry a step, regenerate documents with the current engine, run the
tests, read code, write a diagnosis.

## Enforcement
1. **`pre_tool_call` hook** (`scripts/hooks/repair-guard.sh`, matcher `write_file|patch|terminal`):
   - blocks file writes to zones 2-4 outside `private/repairs/*/worktree`;
   - blocks terminal commands that write outside zone 0-1 in obvious ways (`sed -i`, `>`/`tee` into protected
     paths, `chmod`, `rm`, `mv`, `git commit` / `git reset` / `git checkout` on the live tree), every `git push`,
     and launching other coding agents (`claude`, `codex exec`, `aider`, ...);
   - `bin/hcb repair apply` is the only allowed writer, and it checks the approval itself.
2. **Tamper check.** A fingerprint of zones 2-4 is stored after each approved apply (and after each Claude Code
   change, via `bin/hcb repair seal`, run by the user's session). Every pipeline run, search run and the daily
   start compare it; on mismatch the system stops preparing documents and tells the user which files changed.
   This catches anything the hook misses (a terminal command can always be disguised; a changed file cannot).
3. **Git pre-push hook** in `.githooks`: refuses a push from a Hermes process (environment marker set by the
   profile), as a second lock.

## Limits
- One open repair per failure; at most two attempts. After that, the repair goes to Claude Code with the
  diagnosis attached.
- A repair never runs while documents for an application are being prepared from the same files.
- Repairs to zone 4 and design changes (new features, architecture) are out of scope: they are Claude Code work.
- Content from job ads, web pages or e-mails never opens a repair; only a failing step or the user's own message.

## As built (2026-11-27)
- `hcb/repair.py`, `bin/hcb repair open|check|classify|card|propose|approve|reject|apply|revert|status|list|seal|verify|guard`;
  `bin/hcb approval record` refuses `repair_*` actions. Tests: `tests/test_repair.py`.
- Hook in the career-buddy profile `config.yaml` (`pre_tool_call`, matcher
  `write_file|patch|terminal|execute_code|skill_manage`, `fail_closed: true`), allowlisted.
- `approve` and `seal` refuse a caller with `HERMES_SESSION_KEY` (a Hermes tool subprocess); the
  career-buddy-buttons plugin (v1.2.0) handles `hcb:rep:a|r|d:<R-id>` and the typed weakening phrase in code and
  stops the phrase before the model sees it.
- Seal: `private/state/repair-seal.json` (zones 2 and 4, tracked files plus the profile config, plugins and hook
  allowlist). Checked first in `bin/hcb engine run` (a mismatch fails the run), in each sweep (`seal` field)
  and at the top of the daily digest. Written by `repair apply`, `repair revert`, `bin/hcb repair seal` and the
  `.githooks/post-commit` of the user's own commits.
- `.githooks/pre-push` refuses a push from a Hermes process (`HERMES_HOME` / `HERMES_SESSION_KEY`).
- Known limit: the terminal check is pattern-based; a disguised command can slip past it. The seal is the
  backstop: a changed protected file stops document preparation and is reported to the user.
