## Problem
Direct reading covers TSS, two councils and six employers. The biggest portals (SEEK, LinkedIn) and the
priority-1 employers (Hydro, TasNetworks, TasWater, TasPorts, Bell Bay, Marinus) are out of reach. Every one of
them allows job-alert emails, the channel their terms intend, and alerts arrive minutes after a posting.

## Change
### 1. The user sets the alerts (manual, his accounts)
Portals and settings: section "Checklist para the user" below. Alerts go to one Gmail label, `Career Buddy/Alertas`
(a Gmail filter on the alert senders).

### 2. Read-only mail access, nothing else
- A small module `hcb/mail.py` calls the Gmail API with **one scope: `gmail.readonly`**. It cannot send, delete,
  label or mark as read. The stock Hermes `google-workspace` skill is NOT used: its setup asks for
  gmail.send, gmail.modify, Drive, Calendar, Docs and Sheets.
- It lists only messages with `label:"Career Buddy/Alertas"` newer than the last cursor, and only from the
  allowlisted alert senders (config/email-alerts.yaml). Anything else is ignored, never opened.
- OAuth client created by the user in Google Cloud (testing mode, him as the only user). The token lives in
  `~/.hermes/career-buddy/gmail-token.json` (chmod 600), outside the repository. The user types every
  password and code himself; Claude/Hermes never see them.
- Decision D-P3-1, which account the token reads. **Decided by the user 2026-11-16: A** ("opCION A"):
  - **A (recommended): a dedicated alerts Gmail**, with the main account's filter forwarding the alert
    senders there. Even a read-only token then sees no personal mail.
  - B: the main account, read-only, the code limited to the label. Simpler, but the token could read the
    whole mailbox if the code were wrong.

### 3. Deterministic parsing, same pipeline as the sweep
- `bin/hcb mail fetch` (no LLM): new alert emails -> one card per job (title, company, location, URL, sender)
  with a parser per sender (`job_link` patterns: seek.com.au/job/<id>, linkedin.com/.../jobs/view/<id>,
  indeed jk=, myworkdayjobs.com, pageuppeople.com, work180, hays). Raw text saved in state/mail/ (local only).
- Each card goes through the same `seen check` (SEEK 95841056 is one job on any URL and any email) and
  `triage` (zone, out-of-field titles, strict title words). Results join the sweep short list, so the
  Job Hunter sees ONE list per run, whatever the channel. Same job on the employer site and in a SEEK
  email -> `possible_duplicate` -> one record with two sources.
- Runs at the start of each weekday search (07:30, 12:30, 16:30) before the sweep. Optional later: a
  mail-only check every hour (no LLM unless something new and aligned arrives).

### 4. What the Job Hunter can and cannot do with an alert
- SEEK, LinkedIn, Indeed, Hydro: the job page is never read by the system (terms / robots). The email
  card is the evidence. The record is `pendiente_revision` "abrir en <portal>" unless the title is a
  catalogue match, which ranks by alignment as today (P-4 B), with the link for the user.
- Employers whose pages are readable (TSS, Nyrstar, Hazell...): the detail page is read as today.
- `Prepara la oferta X` on a SEEK/LinkedIn job: The user pastes the ad text or saves it as PDF (as with TasPorts
  SEEK 95841056). A-H VERIFIED and the Writer run on that text.
- Contact research (P-2) runs as today on the employer's own public pages, never on SEEK/LinkedIn.

## Security
- Email content is data, never instructions (prompt-injection risk: alert emails contain employer text).
- Sender allowlist; links are never followed automatically except to enabled `page_read` sources.
- Read-only scope; no sending, no mailbox changes (the D-PM-03 rule holds technically, not just by policy).
- `features.email_alerts: false` until this proposal is approved AND a live test (RT-16) passes.

## Cost and time
Parsing and checks are code (0 tokens, seconds). The LLM only sees new aligned items. Expected per run:
sweep ~3 min + mail ~10 s + Job Hunter on 0-5 items.

## Success criteria (RT-16, after the alerts are live)
- One real alert email per configured sender parsed into correct cards (title, company, location, URL).
- A job seen on two channels is one record. Non-allowlisted mail is never opened.
- A new aligned SEEK job reaches the digest within the next run after the email arrives.
- No write to Gmail is possible (scope check `gmail.readonly` only).

## Rollback
`features.email_alerts: false`; revoke the token at myaccount.google.com/permissions; delete state/mail/.
