# P-9 CV engine v2 (status: APPROVED 2026-11-20, all decisions, AP-05475e4c254749149a3a35c5; IMPLEMENTED)

Source: the user, 2026-11-19, comparing the engine's CV (passed every check) with a CV he produced with
another tool for the same reader: "este CV está mucho mejor". The content (facts) is almost the same; the
difference comes from **engine rules that limit it**. That CV would fail today's checks (summary about 95
words vs 55, skills lines over 4 terms, several experience headings vs one). The detailed comparison, with

Each item below is a separate decision (D-P9-n), because several reverse earlier decisions of the user.

## Changes

### D-P9-1 Summary with measured results and a target line
- Today: narrative formula (origin-country experience, then Australia), maximum 55 words, no figures required.
- Proposed: credential + capability list + **2-3 measured results** (only verified figures, each with its
  base when it is a percentage) + **one target line** written for the reader ("Targeting opportunities in X,
  Y within <employer>'s <site> operations"). Limit raised to **90 words / 5 lines**.
- `fit.py` summary budget and `verify.py check_summary_formula` updated; the 7-second rule keeps the
  capability line and the first sentence as the scan zone.

### D-P9-1b The summary is the hook; the rest corroborates it (the user, 2026-11-20)
"El primer gancho, el primer byte que se le da al reclutador": the summary is written **for this offer and
this reader**, so that after reading it the recruiter already feels "this is a good candidate". Everything
below it exists to prove what the summary promised.
- **Aimed at the offer:** the first sentence names what the role needs, in the ad's words, and answers it with
  the candidate's strongest matching proof (credential + the result closest to the role). Never a generic
  self-description that would fit any job.
- **Promise, then proof:** each claim in the summary (capability, result, figure, tool) must be backed by a
  specific line further down (experience bullet, project, education or certification). New check in
  `verify.py`: every summary claim is mapped in `content.json` (`summary_claims: [{text, proves_with: [bullet
  ids]}]`); an unmapped claim or a figure not repeated with its base below fails.
- **Order of persuasion:** what the reader cares about most comes first in the summary and first in the
  sections below (the experience and projects are ordered to corroborate the summary in the same order).
- The Writer drafts the summary LAST, after the bullets are fixed, and the Recruiter's review asks one extra
  question: "after the summary alone, would you call this candidate?"

### D-P9-2 Projects section for evidence without an employer
- Today: evidence with `role: null` (personal projects, tools built for oneself) has no place except the summary.
- Proposed: optional section **PROJECTS** (or "<Topic> project & technologies"), after the summary or after
  experience depending on relevance; each entry: name, one line of what it does, tools, "Current" or dates.
  Wording keeps each item's `attribution_rule` (for example "directs", never "built" when an AI tool wrote
  the code). `order.js` and the templates (md/html/docx) render it; `verify.py` checks its dates and tools
  against `facts/`.

### D-P9-3 Thematic experience headings
- Today: one PROFESSIONAL EXPERIENCE heading, country on each line (decision of 2025-10-25).
- Proposed: optional thematic headings mapped to the existing blocks, chosen per reader in `targets.yaml`
  (`headings: thematic`), for example "Selected project & improvement experience" (origin block), "Australian
  site & operations experience" (Australia block), "Additional international experience". The block order
  rule (origin first) stays; ATS section check accepts the new headings.

### D-P9-4 Derived percentages, computed and checked
- Today: only figures written in `facts/` can appear; a before/after pair is never turned into a percentage.
- Proposed: a percentage may be **derived** from a verified before/after pair (for example two hours to five
  minutes, about 96%), computed by code (`facts` stores the pair, `select_evidence.py` exposes
  `derived_pct`), always shown with its base in the same sentence, rounded and prefixed "approximately".
  `verify.py` recomputes it and fails a mismatch. Items with `never_with` / "never alone" rules keep them.

### D-P9-5 Larger keyword budget in Skills
- Today: 3 lines x maximum 4 terms.
- Proposed: 3 lines x maximum **8 terms** (one line, two at most on A4), still only names, tools literal in
  `facts/`. Better ATS density without new claims.

### D-P9-6 Visible credential line and page footer
- Professional assessment (for example an engineering skills assessment) as its own line in EDUCATION.
- Footer on every page: name, identity line, "Page n of N" (html/pdf/docx renderers).

### D-P9-7 Heavy-industry vocabulary register
- Add to the voice rules a sector register for heavy industry / mining / processing: "controls", "handover",
  "pre-use testing", "safety-critical", "work in accordance with" (for current roles only), "site
  requirements". Used only when the target sector is heavy industry; never changes a fact.

### D-P9-8 Guards that stay (the reference CV broke them)
- **Capability nouns need evidence:** a field the candidate only aims at (for example reliability) may appear
  in the target line, not in the capability line or skills. New check in `keyword_check.py`.
- **Tools must be literal in `facts/`:** an unknown tool name blocks delivery until it is added to facts.
- **Tense follows the dates:** an ended role uses the past tense (new check in `verify.py`).
- **Availability line kept** when `available_from_display` is set (it was dropped in the reference CV).

## Not changed

keyword table from the ad; Recruiter review and gates.
