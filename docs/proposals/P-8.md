# P-8 Semantic matching for job triage (status: PROPOSED, 2026-11-19)

Source: the user, 2026-11-19: "una búsqueda semántica mejoraría notablemente la búsqueda de trabajo";
employers invent job titles. Evidence from this week:
- **Missed:** "Asset Management & Maintenance Cadet / Graduate" (Stornoway): duties match 4 target roles,
  title matched none -> would have stayed in "pendiente de revisión".
- **Let in:** "Library Operations Coordinator": "Operations Coordinator" is a target title, the job is a
  library one. Fixed by hand (library -> out of field).

## Problem
Triage matches titles word by word against `config/job-targets.yaml`. It cannot see that two different
titles describe the same work, or that a matching title hides another profession.

## Change
### 1. Hybrid, not a replacement
- **Hard rules stay first and are never overridden by a score** (the user's decisions): zone, Senior / Lead /
  Principal / Manager, other professions, expired, expressions of interest.
- **Semantic score decides the grey zone:** a card that passes the hard rules gets a similarity score against
  (a) each target role described by its duties, not only its title, and (b) the user's evidence summary.
  High score + odd title -> read the ad (today it is skipped on strict boards); matching title + low score on
  duties -> "revisar funciones".

### 2. Store: Chroma, embedded
- Chroma runs inside the same Python process, no server; data in `private/vectors/` (gitignored). Works the
  same on the Mac and on Hostinger. Scale is small (about 100 target roles, 60 evidence units, hundreds of
  ads), so heavier options (Weaviate, Milvus, Cassandra, OpenSearch) are not needed, Pinecone would send the
  profile to a third party, and Baserow's internal Postgres must not be modified.
- Collections: `target_roles` (title + duties + group), `evidence` (from `private/facts/`, digest form),
  `ads_seen` (card text of every scanned ad, with the user's decision as metadata).

### 3. Embedding model: decision D-P8-1 (the user)
- **A. Local model** (for example a small sentence-transformers model): free, nothing leaves the Mac,
  slightly less precise, ~100-500 MB download.
- **B. OpenAI embeddings** via the existing provider: more precise, small cost per run, ad and profile text
  leave the machine.

### 4. Measure before switching (no change goes live without this)
- Labelled set: the 238 ads scanned 13-19 Nov with the user's decisions (kept / excluded and why), plus the
  title choices of 2026-11-17 (Project Officer yes, Remote Feed Operator yes, Library no, Senior no...).
- Compare today's rules vs hybrid on: offers the user wanted that were missed, offers let in that the user
  rejected, detail pages read per run (cost/time). Go live only if misses drop and noise does not grow.
- `bin/hcb semantic eval` prints the comparison; `bin/hcb semantic index` rebuilds the collections.

## Cost and time
Indexing a few hundred short texts takes seconds to a minute; one query per card is milliseconds (local
model) or a small API call batch (OpenAI). The sweep stays without LLM calls.

## Success criteria
- On the labelled set, the hybrid finds the Stornoway-type roles (odd title, matching duties) and rejects the
  Library-type ones, with no increase in excluded-but-read ads.
- Hard rules unchanged: no Senior/Manager or other-profession ad ever passes because of a score.

## Rollback
`features.semantic_triage: false` -> pure rules as today; delete `private/vectors/`.

## Decisions for the user
- D-P8-1 embedding model: A (local, recommended to start) or B (OpenAI).
- D-P8-2 threshold policy: start in "shadow mode" (scores logged and shown in the report, not deciding) for
  one week before letting the score decide (recommended).
